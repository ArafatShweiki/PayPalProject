# PayPal Sandbox wallet funding

This checkout moves PayPal **test** funds and credits an internal test ledger. Dream Piggy Bank does not take bank deposits, hold real customer funds or offer withdrawals. The server host is fixed to `https://api-m.sandbox.paypal.com`; no live switch was added. PayPal login through Auth0 is a separate integration and retains its existing `paypal-sandbox` connection.

## Configure

1. Apply all `supabase/migrations` in order to the intended project, including `202610300001_account_state_funding.sql`. Keep RLS and existing grants. Do not reset an existing database.
2. Complete the existing Auth0/Supabase Third-Party Auth setup. Set `AUTH0_ENABLED=true` and `SUPABASE_ENABLED=true` only with valid configuration and schema.
3. In [PayPal Developer Dashboard > Apps & Credentials](https://developer.paypal.com/dashboard/applications/sandbox), select **Sandbox**, then the REST application belonging to the receiving Business test account. Copy its Client ID and Secret to backend environment variables `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET`. Find the same Business account's merchant/account ID under [Sandbox Accounts](https://developer.paypal.com/dashboard/accounts), account details or its Sandbox account profile, and set `PAYPAL_MERCHANT_ID`. It is not the Personal payer's ID or the Auth0 subject. The public Client ID is delivered to the authenticated browser for SDK initialization; the Secret stays exclusively on the backend. Never use a frontend `VITE_` secret or change the Auth0 login connection to configure checkout.
4. Set `APP_ORIGIN` to the exact frontend origin, including scheme and port. Return/cancel URLs are generated server-side from this origin.
5. Use `PAYPAL_FUNDING_CURRENCIES=USD,ILS` to offer both currencies during Sandbox testing. The current local configuration enables both after successful real merchant-bound order creation and SDK eligibility checks. Complete an ILS test capture with a distinct Personal Sandbox payer to verify receiving preferences fully. Both are documented PayPal currencies, but account-specific acceptance can still fail at approval/capture. JOD is not offered for direct funding.
6. Optional: `FUNDING_MAX_MINOR=500000` limits each order to 5,000.00 units of either supported currency. The minimum is 1.00; the hard maximum is 100,000.00. `RATE_LIMIT_FUNDING=10` limits all funding reads/actions per verified user per minute, in addition to existing private and entry limits.

Missing credentials/merchant ID, or a configuration with no supported currencies produces a clear Checkout configuration message in the dialog. Development logs emit `paypal_funding_unavailable` with missing variable names only. Provider connectivity and credential rejections have safe diagnostics without tokens, headers or response bodies. It never enables a local credit button. Browser configuration contains no Checkout secret. Existing Auth0 connections and Supabase key aliases are preserved. Restart the backend after editing environment variables.

## Normal flow

Home and My Wallet open one shared dialog with currency, amount, limits, payment method and summary. The dialog lazily loads PayPal's supported JavaScript SDK v6 from `https://www.sandbox.paypal.com/web-sdk/v6/core`, checks eligibility, and renders its `paypal-button` web component. It starts the payment session directly in the click handler to preserve popup activation while the backend creates an owned durable order. Approval calls the authenticated backend capture endpoint using the local funding ID bound to the returned provider order. Cancellation and errors do not credit the wallet. The dialog shows verified success and capture reference, then refreshes authoritative wallet balances and activity. Failed SDK loading can be retried. Existing redirect return/cancel handling remains available for previously created orders; return parameters never authorize a balance change.

`POST /api/funding/orders` strictly validates request ID, supported currency, exact decimal precision and limits. `POST /api/funding/:id/capture` retrieves and verifies the provider order before capture, uses the same stable capture key on retries, then retrieves the canonical order again. The server requires its own order ID, merchant ID, custom/invoice IDs, exact amount/currency, a single full capture, and completed order/capture status. The SQL credit operation atomically claims the globally unique capture, writes balanced postings and marks the order completed. The UI reloads the authoritative account state.

`GET /api/funding` lists the signed-in owner's attempts and configuration. `POST /api/funding/:id/reconcile` safely checks an uncertain payment; it never captures a merely approved order. `POST /api/funding/:id/cancel` records local cancellation after checking for an existing capture. Cancellation is not a refund. Pending/failed/canceled attempts have no financial postings. An already completed provider capture is recovered as completed rather than discarded because the browser closed or requested cancellation.

Funding appears in existing Wallet Activity with amount, currency, timestamp, status, PayPal source and provider reference. It affects available balance only, with zero savings allocation. Existing purchases still drive round-ups and report spending. JOD remains usable through existing internal test conversions when rates and source funds are available.

## Recovery and refunds

- Duplicate callbacks, reloads and concurrent retries cannot create a second credit: request fingerprint binding, provider keys, unique capture constraints, wallet locks and one transactional SQL commit protect the ledger.
- If capture succeeds but the database write fails, the durable row still holds the provider order. Choose Check status to retrieve the capture and retry persistence; the existing capture is not captured again.
- If an order-creation response/persistence is lost before its provider ID is saved, retry with the same funding request key promptly. Creation retries stop after five minutes to avoid recreating uncertain orders after provider key retention. An unbound request beyond this limit needs operator inspection; do not generate a replacement credit or reset its key. Keep the funding ID for support.
- If the provider reports a full capture refund, reconciliation verifies the capture ID and exact amount/currency, then applies one balanced reversal. Insufficient available funds or a partial/refused capture after credit sets `REFUND_REVIEW`; subsequent private mutations are blocked until it is resolved. Never make a wallet negative or guess a partial refund amount.
- This implementation does not initiate provider refunds, register webhooks or run an automatic refund worker. Reconciliation happens on an owned callback/status check. Operator resolution of partial refunds and aged unbound requests remains a controlled database/provider maintenance task. Do not enable real-money service using this recovery model.

## Merchant acceptance checklist

Use distinct personal and business Sandbox accounts. Verify USD create/approve/capture and, before enabling ILS, its complete merchant capture flow. Repeat the same callback, perform concurrent retries, cancel approval, inspect a pending/failed attempt, and simulate a database outage followed by reconciliation. Confirm that only one owned ledger credit exists, available balance changes exactly once, savings remains unchanged, and another signed-in user cannot read/capture that order. Test a provider-side full refund with status reconciliation and an insufficient-balance review case. Automated provider fixtures are not a substitute for these external checks.

The backend creates the selected currency order and verifies the same amount/currency on the completed canonical capture; SQL posts only to that currency's wallet. No new SQL migration or RLS changes are required.

Real Sandbox Orders v2 requests for the configured merchant succeeded for USD 1.00 (`1SL28631AW0977536`) and ILS 1.00 (`7RA74380W39050132`); both responses matched the configured merchant and requested currency.
